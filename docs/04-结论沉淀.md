# 模块四 · 结论沉淀

> 前端：`src/views/sediment/SedimentView.vue`（1023 行）
> 后端：`server/src/routes/sediments.js`
> 支撑：`src/api/index.js`(sedimentApi)、`PROBLEM_CATEGORIES`(src/data/mock.js)、`server/src/routes/tickets.js`(采纳时写入)

> 定位：归因知识库，承接工单采纳（模块三）自动入库，支持手动新增/编辑/检索/转工单

## 二、交互逻辑链

### 2.1 列表加载
```
onMounted(loadData):
  ├─ Promise.all[sedimentApi.list(), .kpi(), .distribution()]
  ├─ 分享链接 → applySedimentShare 还原 UI 状态
  └─ detailOverlay 持久化 → 自动 reopenDetail
```

### 2.2 筛选逻辑（前端）
```
filtered = SEDIMENTS
  .filter(kw 命中 标题/结论/描述/标签名/标签ID)
  .filter(catFilter 命中 category)
  .filter(indFilter 命中 industry_l1)
  .filter(resultFilter: real_fp/machine_right/updated)
```
- `isUpdated(s)`：有 `updates` 数组即视为已更新。
- KPI 卡点击：`toggleResult` 再点取消筛选。

### 2.3 新增/编辑
```
openCreate → editMode='create' → saveEdit → sedimentApi.create
openEdit(s) → editMode='edit' → saveEdit → sedimentApi.edit(id, form)
  → 刷新 detail（若开着）
  → loadData
```

### 2.4 转工单
```
openToTicket(s) → sedimentApi.toTicket(id)
  → 后端构建 samplesData（related_materials → 素材格式）→ 插 tickets（status=submitted）→ 写 timeline
```

### 2.5 采纳联动（来自模块三）
- 工单 `adopt` 时后端 `tickets.js` 写入/更新 `sediments`（见模块三 §2.4）。
- 沉淀库 `tag_id/tag_name/industry/result_type/conclusion/fp_reason/related_materials` 均来自工单。

## 三、UI 设计要点

- 页头「结论沉淀 / 归因知识库 · 全文检索 · 行业与问题分类分布 · Word 导出」+ 分享/汇总导出/新增按钮。
- 4 KPI 卡（可点击筛选，active 高亮）+ 角标「查看全部/点击筛选」。
- 主区两栏：左结论库（搜索+时间窗口+分类/行业 select+视图切换；卡片/列表）；右图表（行业分布 + 分类分布）。
- 卡片：标签徽章 + 行业 + 结果类型 + 问题分类 + 入库日期；结论摘要；提需/处理人；导出/删除（管理员）；「已更新」角标。
- 详情 Modal：①问题描述 + 关联素材网格（缩略图点击放大预览，视频倍速）②专家结论 ③误杀原因 ④处理信息 ⑤更新记录时间线。
- 编辑 Modal：完整表单；关联素材 URL 输入 + 列表（增删）。
- 素材预览 Modal：大图/视频 + 倍速切换（SPEED_OPTIONS）。

## 五、后端实现（sediments.js）

| 路由 | 方法 | 要点 |
|------|------|------|
| `/` | GET | 列表（is_demo=0，按 adopted_at 倒序）+ `withUpdates` 补 related_materials/updates |
| `/tags` | GET | 标签下拉（去重 tag_id/tag_name，须在 `/:id` 前） |
| `/search` | GET | 多字段 LIKE + 标签精确 + 行业 + 结果类型（须在 `/:id` 前） |
| `/:id` | GET | 详情 + updates |
| `/:id/update` | POST | 轻量更新（结论/结果类型）+ 追加 updates |
| `/` | POST | 新增（requireRole submitter/admin；title 必填；related_materials JSON） |
| `/:id` | PUT | 全量编辑（requireRole submitter/admin）+ 追加 updates |
| `/:id/to-ticket` | POST | 转工单（构建 samplesData → 插 tickets → timeline） |
| `/:id` | DELETE | 管理员删 + 删 updates |
| `/stat/kpi` | GET | 总数/真实误杀/机审正确/已更新 |
| `/stat/distribution` | GET | 行业（`industry_l1` 非空）+ 问题分类 真实聚合 |

### 5.1 `withUpdates(s)`
- 解析 `related_materials` JSON → `relatedMaterials` 数组。
- 返回 updates 时间线（by_user/reason/at）。
- 字段映射：`tagId/tagName/tags(industry_l1? 实际为数组)/industryL1/industryL2/.../dcId/opsAdvertiserName/fingerprint/reviewerName`。

### 5.2 distribution 行业过滤
- 仅 `industry_l1 <> ''` 计入行业分布，避免被污染的 `industry` 字段（误写素材类型/文本）污染行业图。

## 八、改造注意事项

1. **时间窗口未后端过滤**：`sedDate` 当前仅 UI 态，列表/图表未传后端过滤。若需「按入库时间筛选沉淀」需后端 `/search` 或 `/` 增加 `adopted_at` 范围过滤（注意 distribution/kpi 也需同步）。
2. **行业分布防污染**：`distribution` 仅用 `industry_l1` 非空聚合，历史数据 `industry` 字段可能含污染值，改造时勿把 `industry` 重新并入分布计算。
3. **与工单强耦合**：沉淀主要由工单采纳写入，字段映射依赖 `tickets.js` adopt 逻辑；改工单字段必须同步 sediments 写入字段。
4. **问题分类写死**：`PROBLEM_CATEGORIES` 为固定枚举（RULE_CHANGE/RULE_UNREASONABLE/MODEL_ISSUE/OTHER），新增分类需前后端同步改 `mock.js` 与筛选下拉。
5. **related_materials 格式**：存储为 JSON 字符串（前端数组），转工单时映射为 samplesData 素材格式（id/mediaUrl/type/ocr/asr/四字段）；改造素材结构需同步映射。
6. **权限**：新增/编辑需 submitter/admin；删除仅 admin。改造权限模型需同步 `requireRole` 与前端按钮显隐（如 `auth.isAdmin` 控制删除按钮）。
7. **Word 导出**：当前 `exportOne/exportAll` 为前端 toast 占位（`toast.success('已导出 Word')`），**实际未实现真实文件生成**（后端 sediments.js 无导出路由）；如需真实导出需补后端 docx 生成（可参考 materials.js 的 export/word 实现）。
